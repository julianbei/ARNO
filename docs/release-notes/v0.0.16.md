# ARNO 0.0.16

**Theme: a correctness release.** One of these is data loss, so this is worth
taking promptly if you edit repositories that might contain a generated file,
a minified bundle or a long template literal. All of it is issue #5.

## Install or update

```sh
curl -fsSL https://raw.githubusercontent.com/julianbei/arno/main/install.sh | sh
```

`go install github.com/julianbei/arno/cmd/arno-mcp@latest` and the image
`ghcr.io/julianbei/arno-mcp:v0.0.16` carry the same build.

## A long line truncated the file it was in

This is the one to upgrade for.

`splitLines` read with a `bufio.Scanner` and never checked `scanner.Err()`. A
line longer than `bufio.MaxScanTokenSize` (64 KiB) ends the scan with
`ErrTooLong` — so the rest of the file silently did not exist.

It is the primitive that 21 call sites read lines through: `read_range`,
`grep`, `find`, symbol extraction, `delete_symbol`, the LSP bridge. The splice
that writes a file back writes exactly the lines it returns. So an edit
anywhere in such a file deleted everything from the long line onwards, and
said it had succeeded.

A 249-line file with one 70 KB shader literal, editing lines 10 to 12:

```
before: 249 lines, 72927 bytes
after:   47 lines,   602 bytes
reported: r1 → r2 · 1 edits across 1 files, +1 -3
```

Fixed: lines are split without a length limit, keeping `bufio.ScanLines`
semantics exactly (split on `\n`, strip one optional `\r`, no empty final
element for a trailing newline).

**If you edited a file with a very long line using 0.0.15 or earlier, check
it against git.** The failure was silent, so nothing in the response or the
logs would have told you.

## An edit kept the file's line endings — now it does

Because the same function drops `\r` and the splice rejoined with `\n`, a
three-line edit rewrote every line of a CRLF file: 200 CRLF endings became 0.
An edit now preserves the terminator the file uses, and whether the file ended
with a newline.

## An anchor copied from a read now matches the file it came from

Every read strips `\r`, so an anchor copied out of one is LF text for a CRLF
file, and the byte-exact match found nothing. `replace_text` refused an anchor
the caller had just verified byte for byte — the most misleading refusal
available.

It now retries the anchor converted to the file's line endings, only when the
exact anchor is absent and the converted one is present, and converts the
replacement with it so an edit cannot introduce mixed endings. An anchor that
is genuinely wrong still fails.

## A failed check now says the edit is still on disk

Rollback covers an edit that failed to *apply*, not one that applied and then
failed *validation*. Issue #5 was filed believing `check: "impact"` had rolled
the corruption back; it never did, and the caller walked away from a dirty
tree believing it was clean.

A failed or timed-out check now ends the response with:

```
the edit is on disk and was not undone — revert it with revert, or fix forward (workspace is at r7)
```

The behaviour is deliberately unchanged. A check often fails for a reason that
predates the edit — an already-broken build, an unrelated or flaky test — and
discarding correct work on that signal would be worse than reporting it.
`checkpoint` and `revert` remain the way to undo on purpose.

## An anchor hint says what its guess rests on

`AnchorHint` pins an anchor on a line that occurs exactly once in the file and
reports where the two part. That alignment is a guess, and stated flatly —
`line 1145 reads ""` — it read as a fact: issue #5 has a caller chasing a line
400 past the block it was editing. The hint now names the line it aligned on
and says the alignment may be wrong.

## Known limitations

- Windows is not supported.
- One server serves one repository, though any of its worktrees (0.0.15).
- Exact references, cross-file rename and type errors on edit need that
  language's server installed; without one ARNO still answers and labels the
  answer approximate.
- Kotlin has no support yet.
- Telemetry is local only and never transmitted.
